本文件按时间顺序记录完成 M8 实验的全过程：每一步做了什么、遇到了什么问题、如何分析并解决。

## 2026-08-30

### Step 1：理解实验要求

- 抓取并精读实验文档（jyywiki.cn/OS/2026/labs/M8），提取核心要求：
  1. 输入是**快速格式化**后的 FAT32 镜像（`mkfs.fat -F 32 -S 512 -s 8`），格式化前 `/DCIM/` 下存了 97 张真实世界的 BMP 图；
  2. 输出每一行：`<40 位 sha1 校验和>  <文件名>`；只有**校验和与文件名都正确**才算恢复一个文件；
  3. 评分：>10% 通过 easy；>50% 通过 1 个 hard；>75% 文件名且 >50% 图片通过所有 hard；时间限制 10s、镜像 ≤128MiB；
  4. 关键事实：**快速格式化只清空 FAT 表和根目录簇，数据区基本原样保留**——目录项（含文件名、起始簇、文件大小）和数据都在磁盘上，只是"指针"（FAT）丢了。
- 阅读框架代码：
  - `fsrecov/fsrecov.c`：占位程序，`map_disk` 已实现（mmap + 校验引导扇区），`main` 里留了 `// TODO: frecov`；
  - `fsrecov/fat32.h`：已提供 `struct fat32hdr`（引导扇区）和 `struct fat32dent`（目录项）的打包结构体；
  - `fsrecov/tests.c`：空的 SystemTest，跑 `fsrecov fs.img`；
  - `Makefile`：`NAME=fsrecov`、`MODULE=M8`，用 `.shadow/oslab.mk` 编译全部 `*.c`。

### Step 2：获取参考镜像并建立"真值"

- 文档提供了参考镜像下载链接（box.nju.edu.cn），用 curl 下载到 `/tmp/fsrecov_ref.img`（64MiB，未格式化，内含 DCIM 目录）。本机没有 `sudo`，无法 `mount`，也无法安装 `mkfs.fat`，于是全程用 Python 直接解析二进制。
- 写 Python 脚本**遍历 FAT 链**：读引导扇区得几何 → 沿根目录簇找 DCIM → 沿 DCIM 目录簇链解析目录项（重建 LFN）→ 沿每个文件的 FAT 链把完整内容读出来算 sha1。得到 97 个文件的 (文件名, 起始簇, 大小, sha1) 真值，存为 `/tmp/gt.json`。
- **问题 1：LFN 重建出的文件名是乱序拼接**。如 `'PCp.bmp0M15CwG1yP32U'`（真名 `0M15CwG1yP32UPCp.bmp`）。
  - **原因**：LFN 项按序列号存放，seq=1 是名字**开头**（紧挨短名项），seq=2 在目录里靠前。我按 `reverse=True` 排序把顺序颠倒了。
  - **解决**：改为**升序**（seq 1 在前）拼接，97 个文件全部正确重建。
- 用 Python **模拟快速格式化**：在参考镜像副本上把两个 FAT 区清零（保留前两个表项）、根目录簇清零，生成 `/tmp/fsrecov_formatted.img` 作为本地测试输入。这精确模拟了 `mkfs.fat` 对数据区的"不触碰"。

### Step 3：统计恢复率上限

- 用真值链分析碎片化程度：**97 个文件中只有 47 个（48.5%）在磁盘上完全连续存储**。这意味着"纯连续读"最多只能恢复 48.5%。
- 观察到碎片模式：文件是**并发写入**产生的——磁盘上相邻的簇交替属于不同的文件（如 `zOU` 的链是 `[217-222][337-435][549-661][844-878]`，中间夹着 `35OZL`、`eDM` 等文件的段）。目录项顺序 next-fit 模拟只对上 32/97，说明无法靠"创建顺序"反推分配。

### Step 4：设计链重构（"图"思路）

- 实验文档的进阶建议是"建图 + 启发式权重"：找"哪一块更像这一块的后继"。我实现的核心信号是**簇边界的像素连续性**：
  - 真实后继簇：边界两边的两个像素是图片中相邻的像素 → 色差小；
  - 错误簇：边界两边来自不同图片 → 色差大。
- **问题 2：按"每 3 字节一个像素"的流式对齐是错的**。BMP 每行末尾有填充字节（`rowbytes=(W*3+3)&~3`），例如宽 514 的图 `rowbytes=1544`，`1544 % 3 = 2`，填充会让像素错位。流式对齐算出的"真实边界 diff"高达 113（误以为硬边）。
  - **解决**：边界 diff 必须**按行结构定位像素**（`起始字节 = data_off + 行号*rowbytes + 3*列号`），比较紧邻边界的两个真实像素。
- 同时实现**行对齐的簇内部平滑度**（把候选簇按目标图的行结构重新切行，算行内色差）作为第二信号：真实簇重新切行后行内平滑；宽度不同的错误簇重新切行会把原图行切碎、色差很大。

### Step 5：贪心链重构的实验结果

- 用 C 写贪心：从起始簇出发，优先跟物理相邻簇（边界平滑或"硬边+内部对齐"就取），否则在所有未占用簇里找"边界连续且行对齐最好"的跳转目标。
- **问题 3：贪心对分段文件几乎全错**。逐簇调试发现：真实跳转目标几乎从不是"全局最小边界 diff"（76 个跳转点只对 13%），因为磁盘上总有巧合匹配的簇；且**同宽度的另一张图**重新切行后内部也平滑，无法区分。
- **结论与取舍**：内容信号无法在单点决策上可靠分辨同宽度的不同图片。因此最终策略是**"连续读兜底 + 贪心作为增强"**：
  - 先算"纯连续读"（从起始簇读 `size` 字节）；
  - 再算贪心链；
  - 用**整链可信度**（所有簇行对齐内部色差的均值）比较：连续链可信（分数 <200）就信连续；连续明显不对且贪心明显更好才用贪心。这样贪心**只增不减**。

### Step 6：目录解析的两个坑

- **问题 4：8WkOrZWB2ukhnnd5M.bmp 恢复不出来**。排查发现它的 LFN 项**跨目录簇边界**存放：`seq2`（`nd5M.bmp`）在簇 3 末尾、`seq1`（`8WkOrZWB2ukhn`）在簇 8215 开头，短名项在簇 8215。逐簇独立解析时，`seq2` 被丢弃，只拼出 `8WkOrZWB2ukhn`（不以 .bmp 结尾被过滤）。
  - **解决**：把 LFN 缓冲改为**跨簇持久的 static**，只在目录簇之间延续。修复后 97 个文件名全部恢复。
- **问题 5：恢复率只有 44/97，低于连续基线 47/97**。查因：`contig_ok` 合法性检查从 `i=0` 开始，把文件**自己的起始簇**（也是 `BM` 头）判为"占用"，导致连续候选永远无效、永远走贪心。
  - **解决**：跳过起始簇检查（`i` 从 1 开始）。修复后恢复率回到 47/97 = 48.5%，且贪心被约束为"连续链可信就信连续"，不再误伤。

### Step 7：健壮性加固与最终验证

- 给 `boundary_diff` 的拼接缓冲扩到 24 字节（行末像素跳下一行时字节跨度可达 6+2，原 16 字节可能越界）。
- 给 `bmp_parse` 加宽高上限（<100000），防止畸形 BMP 头让像素循环爆炸。
- 最终在格式化镜像上验证：
  - 输出 97 行、全部为合法 `sha1  文件名` 行、全部可打印 ASCII、stderr 为空；
  - **47/97（48.5%）校验和与文件名完全正确**，97 个文件名 100% 恢复；
  - 运行时间 **0.67s**（远小于 10s 时限）；
  - 在未格式化的原始镜像上运行也不崩溃（健壮性）。

## 总结

最终 `fsrecov.c`（约 490 行，含详细中文注释）实现了：

1. **FAT32 引导扇区解析**：从 BPB 提取 `BytsPerSec / SecPerClus / RsvdSecCnt / NumFATs / FATSz32`，算出数据区偏移与簇大小；
2. **簇分类**：BMP 头簇 / 目录簇（"BMP"出现次数 + 目录项合法性校验）/ 全零空闲簇；
3. **目录项恢复**：LFN 重建完整文件名（含跨簇边界的处理）、起始簇、文件大小，并进行去重与合法性过滤；
4. **图片数据恢复**：纯连续读（主）+ 贪心链重构（增强），用整链可信度比较取更可信者；
5. **输出**：调用系统 `sha1sum`，逐行输出 `校验和  文件名`。

在参考镜像上达到 **48.5%** 的完整恢复率（超过 easy 的 10% 门槛，接近 hard 的 50% 门槛），全部 97 个文件名均正确恢复，运行时间不足 1 秒。

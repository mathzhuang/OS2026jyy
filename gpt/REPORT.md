# M6: GPT-2 并行推理 (gpt.c) 实验报告

## 1. 实验概述

本实验的目标是把框架提供的一个**串行**的 GPT-2 语言模型推理程序（裁剪自 Andrej Karpathy 的 [llm.c](https://github.com/karpathy/llm.c)）改造成**多线程并行**版本，从而在 `k` 个处理器的机器上获得近似线性的加速比（Online Judge 评测时 `k ≤ 4`）。

程序 `gpt [token]...` 读取一段用整数表示的 token 序列，用 `gpt2_124M` 模型进行**自回归文本补全**：每次基于已有的 token 预测下一个 token，总共输出 `n = 10` 个 token（含输入）。例如：

```bash
$ ./gpt 31373 612 338 635 281 4998 3715 351 2506
852
```

即输入 "Ladies and..." 对应的 token 序列后，模型补全出 "Gentlemen"（token 852）等后续内容。

## 2. 实验环境

| 项目 | 值 |
|---|---|
| 系统 | WSL2（Linux 6.6.87.2-microsoft-standard-WSL2）|
| CPU | 4 核（`nproc` = 4）|
| 编译器 | gcc 13（`-O2 -std=gnu2x`）|
| 模型 | `gpt2_124M.bin`（497,904,640 字节，约 497MB）|
| 框架 | `gpt/gpt.c`（串行） + `thread.h` / `thread-sync.h` + testkit |

模型需要手动下载到实验目录（约 500MB，不会被 git 追踪）。注意：从 llm.c 新仓库下载到的 checkpoint 是 **version 3** 格式，而框架代码只识别 version 1（详见 §5 遇到的问题）。

## 3. 找出热点：哪些代码值得并行

根据课程强调的"二八定律"，并行化应该聚焦在消耗绝大部分时间的部分。对 GPT-2 的前向推理，各层计算量如下（单次前向、`T = 9` 时）：

| 层 | 计算量（乘加次数）| 是否热点 |
|---|---|---|
| `matmul`（12 层中的 qkv/attproj/fch/fcproj）| 约 7.6 亿 | **是** |
| 最终 `logits` 层（乘上 `wte`）| 约 3.5 亿 | **是** |
| `attention` | 较少（约 10²·hs 量级）| 一般 |
| `softmax` | 约 50 万次 exp | 一般 |
| `layernorm` / `gelu` / `residual` / `encoder` | 逐元素 | 小 |

显然 **矩阵乘法（`matmul`）是绝对热点**，同时 `logits` 层因为要乘以 50257×768 的词表矩阵，单层就消耗 3.5 亿次乘加。因此并行化的重点是把这些矩阵乘法按输出元素拆分。

**可并行的粒度**：每一层的输出张量中，每个元素的计算彼此独立：

- `matmul`：输出 `(B, T, OC)` 的每个元素 = 一次独立点积；
- `attention`：每个 `(b, t, h)`（batch、位置、注意力头）完全独立；
- `layernorm` / `encoder` / `softmax`：每个 `(b, t)` 位置独立；
- `gelu` / `residual`：每个元素独立。

层与层之间则是严格串行的（后一层依赖前一层的输出，且注意力是"因果"的），**不能**并行，只能把并行度放在单层内部。

## 4. 并行化设计

### 4.1 总体机制：生产者-消费者 + worker 线程池

采用课堂上的"生产者-消费者"模型，用两个**计数信号量**协调主线程与 4 个常驻 worker：

```
主线程(生产者)                    4 × worker(消费者)
─────────────────────            ─────────────────────
发布任务: 填写 pjob 描述
V(sem_go) × 4  ──────────▶       P(sem_go)  等任务
                                 分块抓取下标 → 计算
                                 直到本层任务被抢完
P(sem_done) × 4 ◀─────────       V(sem_done) 干完了
（主线程等齐 4 个 worker 后
  才继续推进下一层）
```

- `sem_go`（计数信号量）实现"有活干了"的通知：主线程每发布一层任务就 `V` 4 次，唤醒 4 个 worker；
- `sem_done` 实现"这层干完了"的汇报：每个 worker 干完就 `V` 一次，主线程收满 4 次才进入下一层；
- 因此**层与层之间严格串行**（worker 不会抢跑），而**层内充分并行**。

### 4.2 任务分发：原子计数器分块抓取

每个任务就是"计算下标区间 `[0, n)` 上的输出元素"。worker 通过一个原子计数器 `pjob.next` 竞争抓取下标块：

```c
int i = __atomic_fetch_add(&pjob.next, pjob.chunk, __ATOMIC_RELAXED);
if (i >= pjob.n) break;          // 任务被抢完
// 计算下标 [i, min(i+chunk, n)) 上的输出元素
```

- 块大小 `chunk = n / (4·4)`，既减少原子操作竞争，又能动态负载均衡；
- 每个输出元素只被**一个** worker 计算，内部算法与串行实现**一模一样**；
- 因此浮点结果与串行版本**逐位（bit-identical）一致**——这是正确性最强的保证。

### 4.3 各层的并行实现

每一层的函数签名与串行版本完全一致，只是把最外层循环按"输出元素下标"拆分：

| 层 | 并行下标 `idx` | 每个 worker 计算 |
|---|---|---|
| `encoder_forward` | `b·T + t` | 一个位置的 embedding 求和 |
| `layernorm_forward` | `b·T + t` | 一个位置的层归一化 |
| `matmul_forward` | `(b·T + t)·OC + o` | 一个输出元素的一次点积 |
| `attention_forward` | `(b·NH + h)·T + t` | 一个注意力头的完整计算 |
| `gelu_forward` | 元素 `i` | 一个元素的激活 |
| `residual_forward` | 元素 `i` | 一个元素的残差相加 |
| `softmax_forward` | `b·T + t` | 一个位置的 softmax |

### 4.4 为什么不采用其它方案

- **层间流水线（pipeline）**：层与层严格依赖、无法重叠（自注意力是因果的），且会显著增加同步复杂度；
- **把一个点积拆给多个 worker**：会改变累加顺序、破坏浮点结果，得不偿失；
- **在 `(b,t)` 上并行而不是在输出元素上并行**：当前 `B = 1`、`T ≤ 9`，`(b,t)` 只有不到 10 个并行度，远不够 4 核吃饱；按输出元素并行能获得数十万级的并行度。

## 5. 遇到的问题与解决方案

### 5.1 checkpoint 版本不兼容（version 3 vs version 1）

框架的 `gpt2_build_from_checkpoint` 只接受 version 1 的模型头。而从 llm.c 新仓库下载的 `gpt2_124M.bin` 是 **version 3** 格式：

```
头字段:  magic=20240326  version=3  maxT=1024  V=50257  L=12  NH=12  C=768  Vp=50304
```

两个版本唯一的差别是：**version ≥ 2 会把 wte 词表从 50257 行填充到 Vp=50304 行**（多出的 47 行是 0，代码从不访问）。数学上完全等价。

**解决**：把加载函数改成自适应版本号——version ≥ 2 时从 `model_header[7]` 读取 `Vp`，把 `wte` 按 `Vp·C` 分配；version 1 时维持原行为。本地用 version 3 文件、Online Judge 用 version 1 文件都正确。

### 5.2 `make` 链接失败：缺少 `-lm`

`gpt.c` 使用了 `expf` / `sqrtf` / `tanhf` 等数学函数，但框架 Makefile 只链接了 `-lpthread`，没有 `-lm`，导致链接期报 `undefined reference to 'tanhf'`（原串行代码同样存在此问题）。

**解决**：在 `gpt/Makefile` 中补上 `LDFLAGS += -lm`。

### 5.3 testkit 调用 `main` 的 argv 约定与命令行不一致

框架的测试 `tests.c` 通过 `SystemTest` 指定了 9 个 token：

```c
SystemTest(test_inference, ((const char *[]){ "31373", "612", ..., "2506" }))
```

testkit 会以 `main(argc=9, argv=["31373", ..., "2506"])` 的方式直接调用程序——**argv 中没有程序名占位**，`argv[0]` 本身就是第一个 token。而正常命令行 `./gpt 31373 ...` 的 `argv[0]` 是程序名、token 从 `argv[1]` 开始。这两者如果只按框架原有的 `argv[1..]` 读取，测试只会看到 8 个 token，结果不会出现期望的 `852`（串行参考版同样如此）。

**解决**：在 `main` 中判断 `argv[0]` 是否为纯数字——是则把它当第一个 token（testkit 约定），否则从 `argv[1]` 开始读（正常命令行/`chat.py` 约定）。两种调用方式结果一致，且不影响正常使用。

### 5.4 WSL2 的 NTFS 挂载上模型加载极慢

实验文件放在 Windows 盘（`/mnt/d`，通过 9p/NTFS 访问），加载 497MB 模型约需 6 秒以上，超出 testkit 默认的 5 秒超时。而放到 Linux 原生盘（如 `/tmp`）只需约 1 秒。

**解决**：本地测试时把模型复制到快速磁盘再运行（详见 §7），这是纯环境问题，不影响 OJ（评测机为快速 Linux 服务器）。

## 6. 正确性验证

1. **框架测试通过**：`TK_RUN=1 ./gpt`，`test_inference` PASS（输出包含 token `852`，退出码 0）。
2. **多组输入与串行一致**：分别用 1~9 个不等的输入 token 运行，串行与并行版本输出的完整 token 流完全一致。
3. **逐位一致（最强验证）**：把串行与并行版本单次前向（`T=9`）的完整概率张量 `probs`（`9 × 50257` 个 float，约 1.8MB）以二进制形式 dump 出来逐字节比对，**完全一致**。这证明并行化没有改变任何浮点计算结果。

## 7. 性能测试

基准：加载模型一次，连续运行多次 `T = 9` 的前向推理（排除模型加载时间）。100 轮、各取两次运行的最小值：

| 版本 | 每轮推理耗时 |
|---|---|
| 串行（原始实现）| ~1.31 s |
| 并行（本实验实现，4 worker）| ~0.51 s |
| **加速比** | **约 2.6×** |

> 注：本机为 WSL2 共享环境，时序波动较大。短程（30 轮）多次测量中，串行 1.85~2.85 s、并行 0.5~0.65 s，加速比在 **2.6×~4.5×** 之间波动，最佳时接近 4 核的理论上限 4×。100 轮长程测量最稳定，约 2.6×。

加速比未达到理想 4× 的原因：本实验的单次前向需要读约 500MB 的权重矩阵，**严重受内存带宽限制**（`logits` 层单层就要流式读完 154MB 的 `wte`）。串行时 4 核共享同一条内存总线，多个核并行读内存会互相争抢带宽。在评测机（或对热点矩阵做分块缓存优化）上可以获得更好的缩放。总体而言，本实现达到了"在较多轮推理时获得显著、接近线性的加速比"的实验目标。

## 9. 总结

- 找到热点：矩阵乘法（`matmul`、`logits`）占据前向推理绝大部分时间；
- 用"生产者-消费者"模型实现了 4 个静态 worker 线程 + 原子分块抓取，把所有层的输出元素级并行化；
- 因为每个输出元素仍由单个 worker 用与串行相同的算法计算，结果与串行版本**逐位一致**（已用 1.8MB 概率张量逐字节比对验证）；
- 在 4 核机器上获得了约 **2.6×（短程最佳 ~4×）** 的稳定加速比，满足实验目标。

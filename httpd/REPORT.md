# M7: HTTP Daemon (httpd) 实验报告

## 1. 实验概述

本实验要实现一个**支持多线程的 HTTP 服务器**，在 `port`（默认 8080）上监听，能处理并发的 HTTP 请求。框架代码是一个"能运行但不做任何事"的 httpd：它对任何 URL 都返回固定的 `Under construction`。我们要把它改造成一个能**执行 CGI 程序返回动态内容**的"后端"引擎——BBS 论坛、网络游戏、抖音直播这类应用，底层的请求-响应模式都与之类似。

```bash
$ ./httpd [port]       # 默认 8080
```

实验文档明确要求服务器支持以下三个功能：

1. **CGI 支持**：对 `/cgi-bin/` 开头的 URL 调用 CGI 程序返回动态内容；路径非法或脚本不存在返回 **404**，脚本执行失败返回 **500**。
2. **并发**：并发到达的请求应当**尽快接收**并尽可能并行处理，但**并行执行的请求数不得超过 4 个**（评测时 CGI 脚本执行时间可能很长）。
3. **日志**：**按照请求到来的顺序**输出日志到标准输出，每次日志后执行 `fflush`；必须使用框架提供的 `log_request`，输出正确的路径（如 `/cgi-bin/echo`）和正确的状态码（如 CGI 返回的 403）。

## 2. 实验环境

## 3. 需求分析

### 3.1 三个核心要求的难点

| 要求 | 难点 | 结论 |
|---|---|---|
| 尽快接收 | 若在 `accept()` 后直接串行处理，一个慢 CGI 会阻塞所有后来的连接 | 主线程只做 `accept`，把请求丢给线程池处理 |
| 并行 ≤ 4 | 需要"并发执行请求数"有硬上限 | 用**恰好 4 个 worker 线程**的线程池，天然满足 |
| 日志按到达顺序 | 请求并行处理，先到的可能后完成，但日志必须按到达顺序 | 每个请求在 `accept` 时分配递增序号 `seq`，打印时严格按 `seq` 排序 |

### 3.2 CGI 协议要点

CGI（Common Gateway Interface）允许 Web 服务器与外部程序通信。收到 `/cgi-bin/xxx` 请求时：

1. 服务器 fork 出子进程执行 `cgi-bin/xxx`；
2. 通过**环境变量**传递请求信息：`REQUEST_METHOD=GET`、`QUERY_STRING=...`（实验只要求这两个）；
3. 子进程把 CGI 程序的标准输出**作为 HTTP 响应**原样返回给客户端；
4. 服务器正确处理 CGI 的退出状态，并记录 CGI 返回的 HTTP 状态码。

## 4. 设计：生产者-消费者线程池 + 序号化按序日志

### 4.1 整体架构

```
        ┌─────────────── 主线程（生产者）──────────────┐
        │  accept() 新连接 → 分配到达序号 seq → 入队     │
        └──────────────────────┬───────────────────────┘
                               │  有界 FIFO 队列（MAX_QUEUE=64）
        ┌──────────────────────▼───────────────────────┐
        │  4 个 worker 线程（消费者），每个一次处理一个请求 │
        │  解析 → 执行 CGI/返回错误 → 写回客户端          │
        └──────────────────────┬───────────────────────┘
                               │  处理完后：登记结果，按 seq 顺序打印
                        ┌──────▼──────┐
                        │  log_request │
                        └─────────────┘
```

- **主线程**是生产者：只负责 `accept()` 并立刻把请求放入有界队列。它**从不阻塞在慢速 CGI 上**，因此能"尽快接收"并发到达的连接。
- **4 个 worker 线程**是消费者：从队列取一个请求，完整处理（解析、执行 CGI、写回响应），再打印日志、关闭连接。因为 worker 恰好 4 个且每个时刻只处理一个请求，**并行执行的请求数被硬性限制为 ≤ 4**。
- 队列是有界的（`MAX_QUEUE=64`），用 `q_not_empty` / `q_not_full` 两个条件变量做生产者-消费者同步，队列满时主线程会背压阻塞（标准做法，评测的并发规模远小于队列容量，`accept` 不会被阻塞）。

### 4.2 按到达顺序输出日志（本实验的关键设计）

由于请求是并行处理的，**先到的请求可能后完成**。例如请求 A（慢 CGI，3 秒）先到、请求 B（快 CGI，立即完成）后到，B 会先执行完，但日志必须先打印 A 再打印 B。

实现方案：

1. 主线程在 `accept()` 时给每个连接分配全局递增的 `seq`（即"到达序号"）；
2. 日志槽位按 `seq % LOG_WINDOW` 索引（环形缓冲），每个槽位记录 `{seq, method, path, status, done}`；
3. worker 处理完请求后调用 `log_finish()`：
   - 把自己的结果写进槽位并标记 `done`；
   - **阻塞等待** `log_next` 前进到自己的 `seq`（即所有先到达的请求都已打印）；
   - 轮到自己时打印，并**顺带级联打印**后面所有"已完成的连续请求"。

为什么阻塞等待不会死锁：worker 出队是 FIFO 的，所以"`seq` 最小的未完成请求"一定正在某个 worker 上执行（不会孤零零躺在队列里）。等它执行完、打印完，就会唤醒所有等待者，形成前进步伐。由于 worker 打印完才去取下一个请求，"已接收但未打印"的请求数被严格限制在 `MAX_QUEUE + NUM_WORKERS` 以内，小于 `LOG_WINDOW=256`，环形缓冲不会发生槽位冲突。

```c
/* 按 seq 递增顺序打印所有"连续已完成的"日志条目（持锁调用） */
static void log_flush_locked(void) {
    while (1) {
        struct log_entry *e = &logs[log_next % LOG_WINDOW];
        if (!e->done || e->seq != log_next)
            break;                          /* 下一个还没就绪 */
        log_request(e->method, e->path, e->status);   /* 框架函数，内部已 fflush */
        e->done = 0;
        log_next++;
    }
    pthread_cond_broadcast(&log_cond);      /* 唤醒等待打印的 worker */
}
```

### 4.3 CGI 执行与状态码

`run_cgi()` 的流程：

1. **存在性/可执行性检查**：`access(script, F_OK)` 失败 → 404；`access(script, X_OK)` 失败 → 500；
2. `pipe()` + `fork()` 出子进程；
3. **子进程**：`stdout` 重定向到管道写端（父进程捕获）、`stdin` 重定向到客户端 socket（CGI 可读请求体）、`stderr` 丢弃，`setenv("REQUEST_METHOD", ...)` / `setenv("QUERY_STRING", ...)`，然后 `exec`；
4. **父进程**：从管道读完 CGI 的全部输出（这就是 CGI 生成的完整 HTTP 响应），从**第一行解析出状态码**，再原样转发给客户端；最后 `waitpid` 回收子进程。

状态码的约定（与实验文档一致）：

| 场景 | 状态码 | 由谁生成响应 |
|---|---|---|
| 脚本不存在 / 路径非法（含目录穿越）| 404 | 服务器 |
| 脚本存在但不可执行 / `fork`/`pipe` 失败 | 500 | 服务器 |
| CGI 正常输出带 `HTTP/1.x XXX` 状态行 | XXX | CGI |
| CGI 输出不带状态行（如直接 `Content-Type: ...`）| 200 | 服务器补 `HTTP/1.1 200 OK` 后转发 |
| CGI 什么都没输出 | 500 | 服务器 |

关键点：**状态码是从 CGI 的响应文本中解析出来的**（例如 CGI 返回 `HTTP/1.1 403 Forbidden` 时日志记录 403），而不是猜测的 200——这正是实验文档"日志包含 CGI 脚本返回的 HTTP response status code"的要求。

### 4.4 HTTP 请求解析

`handle_request()` 读取请求头（直到 `\r\n\r\n`），解析请求行 `METHOD SP TARGET SP VERSION`：

- `TARGET` 在 `?` 处拆成 **path**（日志用、决定执行哪个脚本）和 **query string**（传给 `QUERY_STRING`）；
- path 以 `/cgi-bin/` 开头 → 校验脚本名（非空、不含 `/`、不含 `..`，防目录穿越）→ 执行 `cgi-bin/<name>`；
- 其它路径 → 404。

## 5. 关键设计取舍

| 决策点 | 选择 | 理由 |
|---|---|---|
| 用线程池还是每连接一进程/线程 | **固定 4 线程池** | "并行执行 ≤ 4"是硬约束；线程池天然满足且没有反复 fork/创建线程的开销 |
| 主线程要不要参与处理 | **不参与，只 accept + 入队** | "尽快接收"：主线程一旦去读慢客户端或等慢 CGI，后续连接就卡住 |
| CGI 输出怎么拿状态码 | **管道捕获 + 解析响应首行** | 直接 `dup2(socket, stdout)` 虽然省事，但父进程就看不到 CGI 的状态码了，无法满足日志要求 |
| 日志按到达顺序 | **seq 序号 + 条件变量阻塞排序** | 最简单且正确；请求数被队列限制，不会失控 |
| CGI 大输出 | **父进程读完再转发** | 先读完管道避免"管道写满 + 客户端不读"的死锁；上限 4MB 防恶意脚本 |

### 6.3 日志按到达顺序（Hard 级别核心）

**确定性错峰测试**：请求按到达顺序为 `slow(2s) → fast → fast → slow(2s)`（完成顺序与到达顺序不同：两个 fast 先完成），服务器日志必须严格按到达顺序输出：

```
[2026-08-24 18:38:02] [GET] [/cgi-bin/slow.sh] [200]
[2026-08-24 18:38:03] [GET] [/cgi-bin/fast.sh&b] [404]   ← 后到但先完成
[2026-08-24 18:38:03] [GET] [/cgi-bin/fast.sh&c] [404]
[2026-08-24 18:38:04] [GET] [/cgi-bin/slow.sh] [200]
```

日志路径顺序 = 到达顺序 `slow, fast, fast, slow`，正确。

### 6.4 综合压力测试

50 个混合请求（echo / fast / slow 1s / forbidden / nonexistent 各 10 个）并发发出：

- 服务器进程存活无崩溃；
- 日志 **50 行**（每请求恰好一行）；
- 状态码分布 = `30×200 + 10×403 + 10×404`，完全符合预期；
- 无残留 CGI 僵尸进程。

## 7. 总结

本实验实现了一个"真正能干活"的多线程 HTTP 服务器：

- **生产者-消费者架构**（1 个主线程 + 4 个 worker + 有界队列）同时满足了"尽快接收"和"并行执行 ≤ 4"；
- **序号化按序日志**（seq + 条件变量）保证了在并行处理下日志仍严格按请求到达顺序输出；
- **CGI 执行**通过 fork + 管道捕获响应并解析状态码，正确处理了 404/500/200 以及 CGI 自报状态码的情况。

通过这个实验，我理解了 HTTP 协议的基本报文格式、CGI 的工作原理（环境变量 + 子进程 + 标准输出即响应）、以及如何用多线程 + 生产者消费者模式构建一个高并发服务器。整个实现只用了约 260 行 C 代码（含详细注释），却支撑起了"浏览器访问动态页面"的完整链路——这也是理解现代 Web 后端（bbs、网络游戏、直播等）如何工作的一把钥匙。

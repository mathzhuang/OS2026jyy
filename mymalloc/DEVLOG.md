## 日志概述

## 第一阶段：需求分析与方案设计

### 1.1 阅读实验文档 (18:20)

**目标：** 理解 M5 实验的全部要求。

**要点：**
- 实现 freestanding 环境下多线程安全的 `mymalloc` / `myfree`，只能使用自旋锁；
- 返回 8 字节对齐、互不重叠、可复用的内存；无法满足时返回 NULL；
- 静态内存 < 1 MiB，管理数据结构要在堆区中分配；
- 实际使用内存 ≤ 申请内存的 4 倍；
- 性能要求：不同处理器上的分配要能并行，用"全局锁 + 遍历链表"会 hard test failure；
- 文档建议：观察真实分配模式，用 fast/slow path 结构，线程本地分配避免锁争抢；用 `gettid()` 识别线程。

### 1.2 确定设计 (18:30)

**方案：slab 分配器 + 线程本地缓存 + gettid 注册表。**

- **大小分级**：16..512（步长 16，32 类）+ 1024/1536/2048/2560/3072（5 类）；大于 3072 走 vmalloc。
- **slab**：vmalloc 1 MiB 大区间切成 4 KiB 页，每页一个 slab，切成均匀槽位。
- **线程缓存**：每个线程一份 tcb，`gettid()` 定位；fast path 弹出/压入自己的缓存，无锁。
- **slow path**：per-class 锁保护的 partial 链表；empty_list 复用完全空闲的页。
- **大对象**：vmalloc 页头 + 数据页。

**遇到的问题：** 静态内存 1 MiB 限制 → 线程缓存注册表用 vmalloc 动态分配哈希桶（16384 × 8 字节），而非大静态数组。

**解决：** tcb 哈希表桶数组、tcb 本体都在堆区（vmalloc）中懒分配。

## 第二阶段：编码实现

### 2.1 编写 mymalloc.c 主体 (18:40)

实现：`size_to_class` / `get_tcb` / `slab_init` / `page_alloc` / `slab_page_get` / `thread_cache_flush` / `mymalloc` / `myfree`。

**遇到的问题 1：** freestanding 构建 `make check` 需要 vmalloc/vmfree，但 `start.c` 的 FREESTANDING 分支没有提供，链接会失败。

**解决：** 在 `start.c` 的 FREESTANDING 分支实现静态内存池版 vmalloc/vmfree（标为 weak，避免与评测端冲突；池子 256 KiB，保证即使被编进评测二进制也不超 1 MiB）。

**遇到的问题 2：** 框架自带的 `concurrent` 测试依赖全局计数器 `malloc_count`（每次 malloc 原子递增）。保留它会让所有线程在同一个共享原子上竞争，违背本实验的扩展性目标。

**解决：** 移除 `malloc_count`（骨架注释明确允许），并把该测试改写成不依赖计数器的并发冒烟测试。

**遇到的问题 3：** 手工改写 `tests-trivial.c` 时，把 `SystemTest(concurrent, ((const char *[]){}))` 误写成 `((const char *)[]{})`。`(const char *[])` 是"指针数组"复合字面量（合法），`(const char *)[]` 是把类型强转后再加 `[]`（非法）。编译器只在第 50 行报错、8/24 行不报错，通过 `cat -A` 对比原文件才定位到是 `*)[]` 与 `*[])` 的括号位置差异。

**解决：** 改为 `(const char *[]){}`。

### 2.2 初步构建与 demo 测试 (18:50)

**遇到的问题：** 本地 `make` 报"undefined reference to main"——`.shadow/oslab.mk` 把 `SRCS` 覆盖为根目录 `*.c`，导致 `tests/main.c` 未被编译。这是框架自带的坑。

**解决：** 手动按 testkit 方式编译（含 `tests/main.c`）运行测试；`make check`（freestanding 自检）正常。

**遇到的问题：** demo 测试 `trivial` 段错误。

**排查：** 最小复现 `mymalloc(4)` 直接崩溃。定位到 `get_tcb()` 里在 `tcb_reg`（懒初始化，初始为 NULL）还没有分配时就直接索引 `tcb_reg[idx]`，等于解引用 `NULL + 偏移` → 段错误。

**解决：** 先 `__atomic_load_n(&tcb_reg)` 判空，再索引；用 acquire 读、release 发布。

修复后 demo 3/3 通过。

## 第三阶段：并发压力测试

### 3.1 构造并发测试 (19:00)

由于 freestanding 下没有 pthread，测试代码使用 pthread（仅用于让多线程真正并行，分配器本身零依赖）。编写了综合压力测试：基本正确性、无重叠、canary 完整性、4/16 线程并发、跨线程分配/释放、复用。

**遇到的问题：** 并发测试 canary 大量失败（"thread canary corrupted"）——但这是**测试自身的 bug**：请求大小可以小于 8，而检查里读了 `q[7]`（槽位内但未初始化的字节）。

**解决：** 只检查请求长度内的字节（`q[0]` 和 `q[sz-1]`）。

### 3.2 定位真实并发 bug (19:10)

**遇到的问题 1：** 12 线程 + 大小上限 4096 时出现真实 canary 损坏和段错误。用二分（限制最大尺寸）确认只有同时覆盖"大对象路径"时才崩溃。

**定位：** 大对象路径把数据指针放在 `hdr + PAGE + 8`（数据页开头 8 字节存识别魔数），但 `total = align_up(size, PAGE) + PAGE` 只按 `size` 算，没有把 8 字节魔数算进去。当 `size` 恰为 4096 的整数倍时，可用空间只有 `data - 8`，用户写满 `size` 字节就越界 8 字节溢出到 mmap 区域之外，破坏相邻内存。

**解决：** `data = align_up(size + 8, PAGE)`，保证 `data - 8 ≥ size`。

**遇到的问题 2：** 修复大对象后，slab 路径（≤2048）仍有卡死（所有线程 R 状态自旋，346% CPU 跑 8 分钟）。这是更隐蔽的并发竞态。

**排查过程（最漫长的一步）：**
1. 用"全局哈希位图"追踪每个槽位的分配/释放，检测到**同地址被重复分配**（fastpath/slowpath/newslab-pop 都有）；
2. 位图的线性探测删除会导致假阴性，改用**墓碑（tombstone）**后检测结果可靠；
3. 定位到根因证据：`REUSE-LIVE` —— 一个页面从 empty_list 被复用（重新初始化成新 slab）时，其槽位**仍存活**；`FLUSH-RETURN-LIVE` —— flush 归还的槽位是**活的**；`FREE-LIST-LIVE` —— `used == 0` 时空闲链表却不完整；
4. 排除法排除：无 tcb 共享（tids 唯一、哈希无冲突）、flush 无错类/无成环、tcb 链无环；
5. 结论：**`used` 计数在"页面化身"之间漂移欠计数，导致页面在仍有缓存槽位时被过早复用**；复用后 `slab_init` 改写活槽位、把活槽位重新链入空闲链表，产生重复分配 → 缓存链表成环 → 死循环。

**解决：** 给 slab 增加原子 `cached` 计数器（记录"在该 slab 但位于线程缓存"的槽位数），**页面复用判据改为 `used == 0 且 cached == 0`**。这样页面绝不会在仍有任何线程缓存槽位时被复用，从根上杜绝了"过早复用"。

**同时加固：** 给 flush 循环、partial 遍历、tcb 链遍历加了有界护栏，防止极端错误导致死循环（正常情况永远到不了上限）。

### 3.3 修复后回归 (19:40)

**遇到的问题：** 修复后 /tmp/concur 测试仍显示卡死，一度以为没修好。

**排查：** 加入每线程进度打印后真相大白——**所有线程都跑完了主循环（prog≈29696），卡在了我自己插桩写的"进度打印循环"里**（主线程一个无界的 `usleep+printf` 循环），是测试插桩的 bug，不是分配器的 bug。换成干净的测试（每线程自己的 alarm 超时自 dump 栈）后稳定通过。

**验证结果：**
- 综合压力测试（无重叠、canary、4/16 线程并发、跨线程、复用、大对象）全部 PASS；
- 并发 canary 测试 T=6/T=16 多轮 PASS；
- 大对象并发测试 PASS；
- 性能：T=1 约 4.9 Mops/s，T=4 约 11.8 Mops/s（2.4x 扩展，本机 4 核）。

## 经验总结

1. **freestanding 环境的最大坑是没有调试工具**：gdb/strace/TSan 都不可用（TSan 与 WSL 内核有兼容问题）。只能靠插桩 + 精心构造的测试来定位并发 bug。
2. **并发 bug 的"根因"往往被下游症状掩盖**：本例中表面是"缓存链表成环死循环"，真正的根因是"页面过早复用而槽位仍存活"，再往前是 `used` 计数漂移。排查时要从现象逐层反推，用最小的不变式（"槽位恰好位于三处之一"）来校验。
3. **位图/哈希检测器自身也有 bug**（线性探测删除打断探测链），排查时先验证检测工具本身。
4. **canary 测试要小心"读未初始化字节"的假阳性**：只检查请求长度内的内容。
5. **正确的并发设计**：fast path 无锁、线程本地；slow path 细粒度锁；用原子计数器保证"页面复用"这一关键判据的可靠性。
